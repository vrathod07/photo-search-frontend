AI Photo Search — Frontend

Static web frontend for a photo album that can be searched using natural language (e.g. "show me cats and dogs"). Users can search photos and upload new ones with optional custom labels.

Cloud Computing and Big Data Systems — Fall 2026, Assignment 3.

The backend (Lambdas, CloudFormation template, buildspec) lives in a separate repo: photo-search-backend.

Live site: http://ai-photo-frontend-123.s3-website-us-east-1.amazonaws.com

Features
Search: type a query such as dogs, show me trees or show me cats and dogs. The query goes to GET /search; matching photos are shown with their labels.
Upload: pick a JPEG/PNG photo and, optionally, comma-separated custom labels (e.g. Sam, Sally). The photo is sent to PUT /photos/{key} and stored in S3. The labels travel in the x-amz-meta-customLabels header, so they become searchable together with the labels Rekognition detects.

How it works
Search (uses the generated SDK)
js
const apigClient = apigClientFactory.newClient({ apiKey });
const res = await apigClient.searchGet({ q }, {}, {});
// res.data = { results: [ { url, labels: [...] }, ... ] }

Each result's url is a presigned S3 link (valid for 1 hour), shown as an <img>.

Upload
js
fetch(`${invokeUrl}/photos/${key}`, {
  method: "PUT",
  headers: {
    "Content-Type": file.type,                  // image/jpeg or image/png
    "x-api-key": apiKey,
    "x-amz-meta-customLabels": "sam, sally",    // only sent if labels were entered
  },
  body: file,
});
The object key is <timestamp>-<filename>, so uploads never overwrite each other.
Upload uses fetch (with the same API and API key) so the raw image bytes are sent unchanged.
After an upload, the photo becomes searchable within a few seconds, once the backend Lambda has indexed it.
Configuration

config.js:

js
window.APP_CONFIG = {
  apiKey: "<API key value>",
  invokeUrl: "https://<api-id>.execute-api.us-east-1.amazonaws.com/v1", // no trailing slash
};
Invoke URL: API Gateway → Stages → v1 → Invoke URL.
API key: API Gateway → API keys → Show.

The API key is visible in the browser by design. It identifies and meters the client; it isn't a secret.

Regenerating the SDK

Whenever API methods change: API Gateway → Stages → v1 → Stage actions → Generate SDK → JavaScript. Unzip it and rename the folder to exactly apiGateway-js-sdk, replacing the old one.

Hosting

The site is hosted on an S3 bucket with static website hosting enabled:

Index document: index.html
Block public access: off
Bucket policy: public s3:GetObject on arn:aws:s3:::<bucket>/*
CI/CD — CodePipeline P2

Any push to main deploys the site automatically:

Source: GitHub (via GitHub App / CodeConnections).
Deploy: Amazon S3 → frontend bucket, with "Extract file before deploy" enabled and an empty deployment path, so files land at the top level of the bucket.

No build stage is needed, because the site is plain HTML/CSS/JS.

⚠️ Each push replaces the bucket's files with the repo contents, so keep config.js and apiGateway-js-sdk/ in the repo up to date.

Running locally

Open index.html directly, or serve the folder:

bash
python3 -m http.server 8000
# then open http://localhost:8000

The API must allow the origin (CORS is set to *).

Troubleshooting
Symptom (browser DevTools)	Cause / fix
apigClientFactory is not defined + 404s for SDK files	The SDK folder is missing or misnamed (e.g. apiGateway-js-sdk 6). It must be exactly apiGateway-js-sdk at the top level
CORS error on upload only when labels are entered	The API's OPTIONS response doesn't allow x-amz-meta-customLabels. Fix it and redeploy the API
Requests still go to an old API URL	Browser cache. Hard-refresh (Cmd/Ctrl+Shift+R) or tick DevTools → Network → Disable cache
403 Forbidden	Wrong apiKey in config.js, or the key isn't in the usage plan for stage v1
Site shows a zip / list of files after deploy	"Extract file before deploy" is off in pipeline P2
